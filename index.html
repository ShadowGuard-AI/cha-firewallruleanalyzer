Two Modes, Kept Apart

This program does two jobs, and the page never blends them. In firewall mode it analyses rule sets from iptables and firewalld to find overly permissive rules and rules that conflict with each other, where conflict covers duplicate rules and rules sharing the same chain, source, destination, protocol, and port while carrying different actions, and it outputs a report with suggested improvements, relying on parsing firewall configuration files with regular expressions.

In benchmark mode it checks a system configuration against a user supplied YAML or JSON rule set, identifies deviations from the settings in that rule set, and reports the remediation text from the rule set.

A file with no iptables or firewall-cmd text is reported as type not detected and the run exits non-zero.

commands

Two Command Lines

python3 main.py firewall <firewall_config> [--output OUTPUT]
python3 main.py benchmark <config_file> <benchmark_file> [--schema SCHEMA] [--output OUTPUT]

Under the first line: firewall_config is the path to a configuration file holding iptables or firewalld rules, and the report defaults to firewall_report.txt.

Under the second line: config_file is the system configuration to analyse, benchmark_file is the YAML or JSON benchmark, --schema is an optional path to a JSON schema used for validation, and the report defaults to benchmark_report.txt. These are the only command lines on the page.

findings

The Firewall Findings

An exact accept everything line in the INPUT chain, -A INPUT -j ACCEPT, is High, with advice to review and restrict the INPUT chain to specific ports and protocols.

A rule in the shape -A INPUT -p tcp or udp --dport a port -j ACCEPT is Medium, all traffic accepted on that port, with advice to restrict to specific source IPs.

Duplicate rule lines among the parsed lines are Medium, counted, with advice to state each rule once.

Two rules that agree on chain, source, destination, protocol, and destination port but differ in their -j action are High, with advice to keep one action for that combination.

On the firewalld side, zone=public is Medium, public zone in use, with advice to review and restrict the public zone or use a more restrictive zone.

Type Not Detected Ends the Run

A file with no iptables or firewall-cmd text is reported as type not detected, the report carries that finding, and the run exits non-zero.

What the Search Cannot See

Detection is a substring search over the whole file, so a comment mentioning iptables sends a firewalld file down the iptables branch, and an iptables-save file whose text never contains that word falls through to type not detected.

The accept everything pattern wants the action immediately after the chain name, so an accept rule carrying any qualifier is not caught by that pattern.

Interfaces Are Not Part of the Key

The conflict grouping leaves out interface, source port, and match extensions, so an ACCEPT on one interface and a DROP on another can be grouped as a conflict that is not one.

benchmark

The Benchmark Findings

Benchmark rules are read from a rules list. Each rule carries a description, a severity defaulting to Info, and a recommendation, with No Description and No Recommendation standing where a rule omits them.

A string check is searched as a regular expression through the configuration text, and a failed search becomes a finding carrying the rule own recommendation. A bad pattern costs that one rule its check and becomes a finding about the invalid regex. It does not end the run.

A dictionary check is read only for file_exists. Any other check type draws a warning and no finding.

The benchmark file must hold a mapping at its top level. Its format is chosen by its file ending, YAML for .yaml and .yml and JSON for .json. When a schema is supplied and validation fails, the run stops with an error rather than reporting partial results.

report

How the Report Is Written

Every report writes one block per finding: Description, Severity, and Recommendation, plus a Check Failed line where one exists, each block closed by a line of twenty dashes. A report with no findings reads No issues found.

A Report That Cannot Be Written Ends the Run

A report that cannot be written raises an error and the run exits 1. An earlier habit of swallowing that error would have let a run claim completion with no report on disk, and the page states the current behaviour in full for that reason.
