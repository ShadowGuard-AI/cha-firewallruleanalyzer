cha-firewallruleanalyzer

The Collating Table. A command line tool that works entirely on saved files, the way a collator works through gathered sheets: it reads a firewall configuration file in sequence and pulls out the doubled sheet, the sheet out of order, and the rule that accepts too much.

The repository main.py
ModesTwo subcommands: firewall, on a saved rule file, and benchmark, on a configuration text against a supplied rule set
ReportsWritten to firewall_report.txt or benchmark_report.txt unless --output names another path
Dependenciesjsonschema 4.17.0 or later and PyYAML 6.0 or later
No subcommandPrints the help text and exits 1, every time

Usage

python3 main.py firewall <firewall_config> [--output OUTPUT]
python3 main.py benchmark <config_file> <benchmark_file> [--schema SCHEMA] [--output OUTPUT]
PartWhat it does
firewall_configPath to the firewall configuration file (iptables or firewalld).
config_filePath to the system configuration file to analyze in benchmark mode.
benchmark_filePath to the YAML or JSON benchmark file.
--schemaPath to the JSON schema file (optional, used for validation of the benchmark file).
--outputPath to save the report (defaults: firewall_report.txt, benchmark_report.txt).
-h, --helpShow help message and exit, at the top level and on each subcommand.

Findings and severities

FindingSeverity
An exact -A INPUT -j ACCEPT lineHigh
A rule accepting one TCP or UDP portMedium
Duplicate rule lines, countedMedium
Two rules agreeing on chain, source, destination, protocol, and destination port but differing in actionHigh
zone=public in useMedium

Every report writes one block per finding, closed by a line of twenty dashes. A report with no findings reads No issues found.

Stated limits

  • The firewall type is detected by a substring search over the whole file, so a comment mentioning iptables sends a firewalld file down the iptables branch. A file with no iptables or firewall-cmd text is reported as type not detected, and the run exits non-zero after the report is written.
  • The accept everything pattern wants the action immediately after the chain name, so an accept rule carrying any qualifier escapes it and is judged only by the port pattern.
  • The conflict grouping leaves interface, source port, and match extensions out of the key, so an ACCEPT on one interface and a DROP on another can be grouped as a conflict that is not one.
  • In benchmark mode a string check is searched as a regular expression, and a failed search becomes a finding carrying the rule's own recommendation. An invalid pattern costs that one rule its check and becomes a finding about the regex. A dictionary check is read only for file_exists; any other check type draws a warning and no finding.
  • Rule severity defaults to Info, with No Description and No Recommendation standing where a rule omits them. The benchmark must hold a mapping at its top level, its format is chosen by its file ending, a schema validation failure stops the run, and a report that cannot be written exits 1.
  • Its near twin by subject collects from the live host with substring tests; this one parses files, counts duplicates, groups conflicts, and runs a benchmark mode the other does not have. The two share no art, fonts, or copy.
